# NCPC legacy baseline

Date: 2026-09-02. Scope: source inspection only; no live Sheet, deployment, or
stateful Apps Script database was read or changed.

## Architecture and storage

| Surface | Storage/model | Current role | Classification |
| --- | --- | --- | --- |
| `Apps Script/Code.gs` v2 | Google Sheets tables created by `initializeNcpcSystem`; Script Properties hold database ID, sequences and catalogue version | Active NCPC administration, review, import, release and read API | Preserve concept; redesign implementation |
| `Apps Script/Index.html` | browser IndexedDB read-through cache | Admin UI acceleration only | Legacy implementation detail |
| `schema/catalog-v1.schema.json`, seeds, `server.mjs` | JSON document / local ignored data file | Older local builder/prototype and validation fixtures | Preserve selected concepts; not the active service contract |
| Standard TradeFlow `NtheembaMapping.gs` | Per-shop `AppState` plus `NcpcPublishedCatalogue` sheet cache | Local approved-release client and fake pending submission/correction lifecycle | Compatibility dependency; not NCPC authority |

The active v2 tables are `CatalogueDomains`, `Categories`, `Organizations`,
`OrganizationRoles`, `Brands`, brand/product organization relationships,
`Products`, `ProductVariants`, `Identifiers`, `ProductAliases`, digital assets,
sources/evidence, `ProductCandidates`, `ReviewQueue`,
`BarcodeVerificationQueue`, import jobs/items, `CatalogueReleases`,
`ReleaseItems`, audit events and sequences. IDs are generated by a per-table
sequence under `LockService` with stable opaque prefixes; product and variant
prefixes are `PRD` and `VAR`.

## Current workflows and evidence

| Workflow | Observed behavior | Confidence |
| --- | --- | --- |
| Product bundle save | Creates/updates a Product, its variants, identifiers and product aliases. Product requires domain/category; variants default to draft. | Confirmed in source |
| Duplicate check | Exact normalized identifier and strong product-name checks; import has a product-local variant duplicate key. | Confirmed; incomplete policy |
| Review/publish | Product review can approve identity, publish, reject or request information. Publish requires a reviewed product and one active variant, then publishes all active variants. | Confirmed |
| Candidate submission | Authenticated `doPost` accepts only `submit_candidate`; it creates a small review-gated `ProductCandidates` record. | Confirmed |
| Barcode verification | Existing normalized identifier is rejected; a pending queue item can later create an active verified identifier. | Confirmed |
| Import | Resumable research-manifest jobs create drafts/candidates and review items; protected TradeFlow fields are rejected. | Confirmed |
| Release/export | A release stores entity/version references for published active products/variants; export rebuilds the current published data instead of reading release items. | Confirmed; snapshot gap |
| Candidate search | Published active product/variant/identifier/alias only, exact barcode or tolerant name matching; public response is allowlisted. | Confirmed by local contract test |
| TradeFlow mapping | Standard reads a manually loaded approved release, verifies `PRD`/`VAR`, then saves local mapping metadata. Pending requests are fake/local. | Confirmed; adapter, not live NCPC |

## Current public and consumer contracts

`doGet` supports `health`, `candidates`/`search`, exact `barcode`, and
`product`. Read results use `{ success, message, data, errorCode? }` and the
candidate contract version is `ncpc-candidate-search-v1`. Candidate results
provide IDs, canonical/variant/brand names, size, sales unit, identifiers,
aliases and matching metadata only. Public routes hard-force published/active
filters. `doPost` requires `NCPC_SUBMISSION_API_TOKEN`, accepts only
`submit_candidate`, and is a review submission—not a general write API.

Standard TradeFlow's replaceable client expects `searchCandidates`, `getVariant`,
`verifyVariant`, `submitProduct`, `getSubmissionStatus`, `submitCorrection`, and
`getCorrectionStatus`. Today only its local approved-release cache implements
those semantics; no live NCPC endpoint is a supported replacement yet.

## ID and barcode baseline

v2 generated IDs are sequential, opaque values such as `PRD-000001` and
`VAR-000001`; sequence state is in Sheets and Script Properties. Existing
references include variants, identifiers, aliases, evidence, release items and
TradeFlow mappings. The older JSON prototype permits descriptive `PRD-*` and
`VAR-*` values, so one historical format is not enough to infer global
uniqueness or migration readiness.

Identifiers are stored as `identifierValue` strings and may be multiple per
variant. The active code compares `normalizeText_` values, which lowercases and
normalizes whitespace; it has no explicit barcode normalizer, symbology
validation, leading-zero test, atomic uniqueness index, provenance type on the
identifier itself, or conflict state. Save/import simply skip an existing value;
verification rejects it. This prevents some duplicates but silently hides a
conflicting claim rather than creating a reviewable conflict.

## Technical debt and non-portable behavior

- Google Sheets rows are weakly typed and scan-based lookups make uniqueness,
  concurrency and large catalogue behavior fragile.
- Product/variant `publicationStatus`, generic `status`, verification state and
  ReviewQueue state can contradict one another.
- Candidate and barcode queues are not a coherent proposal aggregate and lack
  an immutable decision history.
- Alias records can point to both product and variant, or neither; no invariant
  enforces exactly one target or normalized uniqueness.
- `ProductVariants.sizeValue/sizeUnit/salesUnit/packagingType` is useful but
  cannot represent pack count/composition cleanly.
- Release items record versions but export is a live reconstruction; release
  snapshots cannot be reproduced or rolled back reliably.
- ID sequence repair/reinitialization, Sheet row replacement and reads/writes
  have Apps Script quota/latency and partial-failure risks.
- `doPost` returns raw error text through `SUBMISSION_FAILED`, unlike the safer
  read/search failure behavior.
- The old JSON schema calls its records `published` while v2 uses separate
  `publicationStatus` and `status`; it also calls barcodes `BAR-*`, whereas v2
  uses `IDN-*` identifiers. Neither is a final migration contract.
